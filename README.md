# validate_fee_payer: x86-64 artifacts for formal verification

Machine code of `solana_svm::account_loader::validate_fee_payer`
(`svm/src/account_loader.rs`) as it appears in a release build of
`agave-validator` for `x86_64-unknown-linux-gnu`, together with every byte of
fixed memory it can reach and the layout of the values it works on.

## Reproducing

Requires Docker; the CI image is amd64-only, so enable Rosetta on Apple Silicon.

```sh
git submodule update --init --depth 1   # agave/, pinned to the commit below
./build.sh            # agave-validator, ~10 min under Rosetta
./make-artifacts.sh   # carve, measure, check -> artifacts/ and lean/ValidateFeePayer/Image.lean
```

Both run in Anza's CI image through agave's `ci/docker-run.sh`, the wrapper
CI uses, which mounts `agave/` at `/solana`; `ci-image.sh` has the pins and
mounts this repository at `/vfp`. `build.sh` runs
`scripts/cargo-install-all.sh`, the release build script. The container's
cargo target dir and registry live in `cache/` (gitignored; override with
`VFP_CACHE`); the binary ends up in `cache/target/install/bin/`.

Deviations from a release build, none of which change code generation:

- dcou dev tools, platform-tools and spl-token are not built;
- `CARGO_PROFILE_RELEASE_STRIP=none` keeps the symbol table;
- `SOURCE_DATE_EPOCH` is the commit time. Otherwise OpenSSL embeds the
  wall-clock build time, which shifts `.rodata` and with it rip-relative
  displacements throughout the binary.
- git is disabled in the container, so `version/build.rs` does not embed
  the commit hash (`solana-version` then reports no commit). This one does
  change code generation: with the hash embedded the binary's sha256 is
  `2f91db73…`, both functions move by `0x6a0` and their rip-relative
  displacements change. A CI release build, which has git, therefore matches
  that variant, not the artifacts here.

Two clean builds from different checkout paths, and a rebuild after moving
agave into this repository as a submodule, produced byte-identical binaries (sha256 `3f0a1e446ba474e54aecd11f33844a73343f460cf275ef40c27659d7ab7fd34d`).

Caveat: Anza's published Linux tarball is built by `ci/publish-tarball.sh`
directly on a release-build agent, not in this image. The toolchain matches,
but the shipped binary has not been compared against these artifacts.

## Artifacts (`artifacts/`)

| File | Contents |
|---|---|
| `validate_fee_payer.bin` | Code of `validate_fee_payer`, `0x230` bytes at `0x27f3560` |
| `check_static_account_rent_state_transition.bin` | Its one callee that was not inlined, `0x19c` bytes at `0x27f3790` |
| `manifest.json` | Addresses and hashes of the code; every data object with its bytes, relocations and meaning; the panic entry point; mnemonic counts; the measured layout |
| `validate_fee_payer.elf` | Code and data at their original addresses, one `PT_LOAD` segment each. Not runnable; for disassemblers and x86 models |
| `validate_fee_payer.{intel,att}.s` | Disassembly of the ELF |
| `standalone.S`, `standalone.ld` | Generated assembler source and linker script for the ELF |
| `SHA256SUMS` | Hashes of all of the above (`lean/ValidateFeePayer/Image.lean` is written by the same run) |

All addresses assume load base 0. The code has no relocations (it is
position-independent), so at base `B` everything moves by `B`, and the three
relocated words (two pointer slots and the panic `Location`'s file pointer)
hold `B + value` instead of `value`. The manifest lists them per object.

## Lean package (`lean/`)

`lake build` in `lean/` (Lean v4.34.1, no dependencies). Two libraries:

- `X86/`: a generic x86-64 user-mode machine with no knowledge of this
  program. `Memory` (sparse mappings with permissions; a bad access is a
  `PageFault`), `Instruction` (the supported subset, chosen by form),
  `Decode` (the encoding grammar; `decode m address` fetches through memory
  one byte at a time, so jumping into the middle of an instruction decodes
  what is there, as on the CPU), `Machine` (`execute`, `step`, `run`), `F64`.
  `step` is parametrised by `Exits`: the return address and the address of a
  non-returning function (the panic). Reaching any other unfetchable address
  is `badJump`.
- `ValidateFeePayer/`: the program. `Image` (generated by the carve tool),
  `Loader` (the image mapped at `loadBase`), `Code` (a linear sweep with the
  generic decoder, used only by checks and proofs), `Checks` (kernel-checked
  facts: regions disjoint, sweep equals llvm-objdump's disassembly, decoding
  from memory equals the sweep), `Spec` (the Rust functions in Lean:
  a panic or a `TransactionError` is an `Error`; `chargeFeePayer` does the
  checks, `validateFeePayer` updates the error metrics from its error), `Contract` (`Encodes` predicates, `Pre`, `Post`), `Correctness` (the
  theorem; its proof is the package's only `sorry`), `Tests` (machine
  against `Spec` on concrete inputs).

The theorem: from any state satisfying `Pre` (arguments where SysV puts
them, each pointing at an encoding of a Lean value, enough free stack,
disjoint objects), `run` with 240 steps of fuel ends in `panicked` exactly
when `Spec.validateFeePayer` throws a `Panic` (`lamports_per_byte` above the
cap for its exemption threshold), and otherwise in `returned` with the
result, the metrics and, on success, the account encoded, callee-saved
registers restored and every byte outside the result, the lamports, three
counters and 96 bytes of stack unchanged.

`check_static_account_rent_state_transition` is carved and called through
its GOT slot like any other code, so it needs no contract. Only
`core::option::expect_failed` is an exit.

Of the 12-byte `Result<()>`, only the 4-byte tag and, for
`InsufficientFundsForRent`, the account index at byte 4 are defined; the
code writes nothing else.

### Modelling decisions

- Undefined flags are `none`, and reading one stops the run (see
  `Stop.undefinedFlagRead` for why that is sound). Entry flags are undefined.
- 16-byte SSE memory operands must be aligned, hence `Pre.alignedBase`.
- Only the default MXCSR control bits are modelled; the sticky exception
  flags are not, since nothing reads them.
- The decoder is strict: it rejects encodings with bits the CPU would
  ignore, so a decoded instruction means exactly its `Instruction`.

## What the carve tool checks (`carve/`)

`carve/` is a Rust program that reads the source ELF, decodes the code with
iced-x86, and links `solana-svm` to measure layouts. Its lockfile is the
workspace's plus `iced-x86`; shared dependencies have the same versions.

- `code.rs`: finds both functions by symbol, then requires that every
  instruction is in `AUDITED_MNEMONICS` (also the instruction set the Lean
  semantics must cover), has no `lock` or fs/gs prefix, branches only to
  instructions of the carved code, and calls only through relocated pointer
  slots aimed at a carved function or at `core::option::expect_failed`. Fixed
  memory may only be read or `lea`'d, and only rip-relative.
- `data.rs`: carves exactly the bytes the code reads, plus the objects whose
  addresses are passed to the panic. Each must be recognised by content (e.g.
  `solana_sdk_ids::system_program::ID`) or by what it points to.
- `layout.rs`: measures `AccountSharedData` (including the `Arc<Vec<u8>>`
  behind it), `Rent`, `TransactionErrorMetrics` and
  `Result<(), TransactionError>` on x86_64-linux, and checks that the `Result`
  tags it measures are exactly the immediates the code stores.

Anything unexpected is an error, so a rebuild that changes code generation is
reported rather than silently carved.

`make-artifacts.sh` then assembles and links the ELF with the image's binutils
and checks that each function disassembles identically, addresses and
rip-relative targets included, in the source binary and in the ELF. That check
uses GNU objdump, a decoder independent of LLVM and iced.

## The panic

`core::option::expect_failed` (`0x12be100`) is not carved. It enters Rust's
panic runtime, which leaves this binary for libc and libgcc. Reaching that
address is the terminal "panicked" outcome. It happens only through
`Rent::minimum_balance`'s `expect`, when `rent.lamports_per_byte` is above
its cap.
